The state architecture, settled

Five research agents, mostly against primary sources: two IETF RFCs, a WHATWG standard, Apple / Android / Google / Slack first-party docs, SQLite's own documentation, and Kafka's design notes. They converge on one architecture — and they identify three specific traps, one of which I was about to walk into and two of which are already live bugs.

The answer

The log is immutable and is the only system of record. Everything else is derived. State lives on two separate axes that must never share a column:

WORLD FACTS  →  the event log        (append-only, never mutated)
                 what happened, in order, per session

USER FACTS   →  a small cursor       (one row per session)
                 how far I have got: heard-through, dismissed-through

WAITING      →  a query              (never a stored value)
                 latest event per session is a Stop,
                 and its sequence > my cursors

That is the whole design. Every bug tonight was a consequence of collapsing those three things into one mutable status column with six writers.

The three traps

1. Ordering by wall-clock timestamps — a live bug

Events are ordered by createdAtMs, a millisecond stamp taken independently by each short-lived hook process. Kafka — the reference implementation of latest-value-per-key — deliberately does not do this. It compacts by offset:

"The offset for a message never changes. It is the permanent identifier for a position in the log."

Timestamp-based compaction exists there only as a non-default opt-in, and even it falls back to offset as a tiebreaker. The failure mode is silent: Kingsbury's worked example has the newer write losing to the older one after a clock step, with nothing surfacing the loss. POSIX time is not monotonic, and NTP is one of the causes rather than the cure.

Fix: INTEGER PRIMARY KEY AUTOINCREMENT. SQLite guarantees those rowids are never reused and monotonically increasing. Plain rowids do not carry that guarantee once rows are deleted. The timestamp stays as data about when the world changed; it stops being the ordering key.

2. Bare-column max() returns the wrong row on ties — reproduced

SQLite documents the guarantee and the hole:

"If the same minimum or maximum value occurs on two or more rows, then bare values might be selected from any of those rows. The choice is arbitrary."

The agent built the case and ran it. A session whose heard and waiting events share a timestamp: GROUP BY sid with max(ts) returned heard — the wrong state, silently. max(id) over the rowid returned the right row and matched the window-function result.

A timestamp collision — two events in the same millisecond, which two hooks firing together will absolutely produce — flips the badge. Aggregating on the rowid closes it, because rowids cannot tie.

Worth noting: the most-cited secondary write-up on this SQLite feature does not mention the tie caveat at all.

3. Dismissal as a boolean — a live bug

Android states the rule plainly:

"If the previous notification is dismissed, a new notification is created instead."

Dismissal is scoped to the instance that existed when you dismissed it, not to the key forever. So a dismissed flag per session is wrong — the next turn from that session must revive it. A dismissed-through-event-id watermark reproduces the platform semantics exactly, and revives by construction rather than by rule.

What the inbox world already settled

The separation I needed has standard vocabulary — it just isn't universal, so I never found it by searching for it directly.

IMAP defines message attributes that "MUST never change" — internal date, size, envelope, body structure, message texts — and separately a flag list, where \Seen means exactly "Message has been read." JMAP tightens it almost to totality: nearly every Email property is marked "(immutable; server-set)", and only keywords and mailboxIds are mutable.

Nobody stores unread. JMAP defines unreadEmails as a count of emails lacking $seen. Gmail is the presence of an UNREAD label. Google Chat compares lastReadTime against the latest message. All queries.

Google Chat is the closest structural match to what I need: read state is a separate resource, users/{user}/spaces/{space}/spaceReadState, carrying nothing but a lastReadTime. Slack is the same shape — conversations.mark sets one cursor per conversation and derives the unread count from it.

Gmail describes my worst bug, and the fix is structural

"Labels only exist on messages… If messages are added to a thread after you add a label, the new messages don't inherit the existing label associated with the thread."

Thread-level unread is a derived aggregate over per-message annotations. So a new arrival makes the thread unread again with no extra logic and no write.

That is precisely the bug where typing a message retired the reply that arrived after it. I kept trying to fix it by adding retirement rules — before: timestamps, includeAnnounced flags — and it kept not working, because the annotation was on the container. Gmail gets it for free by never annotating the container at all.

Supersession is a key, not a stored fact

Android replaces on (tag, id). Apple replaces on identifier. APNs merges on apns-collapse-id. WHATWG specifies it as an algorithm over a list. Four platforms, one mechanism: a caller-supplied identity key, newest wins.

But the agent caught the category error I was about to make. Those platforms destructively mutate because they have no log underneath — the coalesced set is their only state. Reading that as an endorsement of storing supersession is wrong. What transfers is the explicit key; the mutation does not.

Also worth separating: grouping is not supersession. Apple's threadIdentifier and Android's setGroup() are display-only, and deliberately different APIs from replacement. And Android's setOnlyAlertOnce() makes a third distinction I had collapsed: "the record updated" and "re-alert the user" are separate concerns.

Compute on read — measured, not assumed

The agent benchmarked the options rather than citing anyone. SQLite 3.51, warm cache, full query = latest per session, filtered to waiting, newest first:

Approach8k events100k events
GROUP BY + bare columns1.13 ms12.61 ms
ROW_NUMBER() in a subquery9.89 ms185.68 ms
correlated subquery over events1.65 ms—
sessions JOIN correlated LIMIT 10.33 ms3.26 ms
pre-materialized projection table0.15 ms—

Window functions are the slowest by an order of magnitude — the plan builds nested co-routines and scans every row. The winner does one index seek per session, so its cost tracks session count, not event count.

So: compute on read. 0.33 ms against a five-second tick is a 0.007% duty cycle. A projection table saves 0.18 ms and costs a schema, a migration, a trigger, and an invariant that can silently drift — which is the exact class of thing that has been biting me all day. SQLite also has no materialized views, so a VIEW buys nothing; the choice is genuinely binary.

Two details that matter more than the shape: put every column the derivation reads into the index (a covering index "can make many queries run twice as fast"), and aggregate on the rowid rather than the timestamp per trap 2.

What I'd build

events            append-only, never updated
  id              INTEGER PRIMARY KEY AUTOINCREMENT   ← the ordering key
  session_id      TEXT                                ← the coalescing key
  kind            TEXT    stop | user_prompt | notification
  created_at_ms   INTEGER                             ← data, not ordering
  payload…

session_cursor    one row per session, one writer
  session_id      TEXT PRIMARY KEY
  heard_through   INTEGER   ← event id
  dismissed_through INTEGER ← event id

waiting = for each session, latest event by id;
          keep it if kind = 'stop'
          and id > max(heard_through, dismissed_through)

No status column. No supersession pass — "superseded" is just "not the latest." No retirement sweep — a user_prompt event is simply a later event, so the session stops being waiting without anything being written. No resurrection bug, because nothing is ever overwritten.

The one genuinely new constraint, from Fowler: replay must not re-fire the voice. Rebuilding the derived view must not announce everything again, so dispatch has to be driven off the diff the derivation produces, never off the events themselves.

What is still uncertain

Per-claim verification did not run. The findings above are quoted from primary sources, but the independent fact-checking pass was skipped for context reasons. The load-bearing claims are direct quotes from RFCs, platform docs and SQLite's own documentation, so I am comfortable acting on them — but that is the one gate this research did not clear.

No source documents multi-writer mutable status columns as a named anti-pattern. The support is indirect: Nat Pryce's retrospective lists "command processors both stored events and current state" as a mistake, with the recovery being a single-writer read-through cache. That is the closest published precedent.

Performance numbers are one machine, warm cache. The ordering between approaches is solid and explained by the query plans; the absolute milliseconds are not gospel.

A lead worth following: IMAP's CONDSTORE extension (RFC 7162) gives each message a MODSEQ and a conditional UNCHANGEDSINCE store, so a racing write fails instead of silently winning. That is the direct precedent for the interrupt handler that resurrected a dismissed row — worth reading before writing anything that can be written from two places.
